# Amazon 场景可操作性检查与演示清单

检查日期：2026-11-06。

## 结论与证据口径

**当前不能验收为“每一条 Amazon 场景均可由用户完整操作”。** 正常主线与部分恢复路径可达，但存在缺修复入口、配置门禁、错误按钮及未实现的生产动作。

本次未修改场景数据、重置用户浏览器或自动修复业务单据。浏览器验证使用全新隔离上下文，不污染用户当前数据。

- 全量 Vitest：47 文件、318 测试通过；TypeScript 检查通过。比上一轮少 1 项是移除了人为预览过期的拒绝用例，不表示覆盖所有场景。
- 浏览器实测：九张销售场景页面可打开；本地/虚拟/平台仓创建、绑定刷新保留、自有仓 2 件 + 剩余 2 件加急 MCF、打包任务撤回后 4 件转 MCF、待映射修复后发货、回传失败重试成功。
- Vendor/DF：正式页面、Provider、命令及数据依赖静态核查；本轮未实际点击完整流程。
- FBA：正式页面/命令核查，并在内存模块执行 SPD/LTL 分仓、接收、差异和取消；本轮未做完整浏览器操作。不能把内存验证称为页面验收。
- 所有外部执行仍是本地提供方，不代表真实 Amazon/WMS/承运商已接入。

## 演示前统一设置

1. 公司选择 Northwind，商家选择 Northwind Amazon US。
2. 在 APP 中检查 Seller / Vendor 授权和对应业务启用状态。
3. MCF 必须先去仓库中心：新增仓库 → 第三方平台仓 → Amazon 供应商 → 对应 US FBA 逻辑库存池。创建名字为 FBA 的普通仓不够。
4. FBA 库存观测必须在 APP 的 Seller FBA 配置开启并**保存**“读取 FBA 库存”。默认样本未持久化此开关，仅打开配置面板不够。
5. Vendor/DF 使用来源仓节点映射；默认节点为本地 DEMO 数据，不是已获 Amazon 验证的真实节点。
6. 样本只首次追加，不会刷新重置。已有发货、取消、库存不足均按实际记录处理，不能保证旧浏览器仍处于下表初始状态。

### 销售场景的具体断点

1. **地址待补不可修复**：订单使用只读通用详情，执行命令无地址更新；提示“请补全”但没有可用操作。
2. **部分发货原包裹回传悬空**：`amazon-sales-scenarios.ts` 在造 partial 场景发货后删除该场景包裹的所有 job；包裹保留 pending。`order-execution.tsx` 只在 failed 显示重试按钮，无法恢复 pending 且没有 queued job 的记录。
3. **回传失败双对象不一致**：样本构造只把 Package 改成 failed，未同时把新 Shipment 改成 failed。重试最终会更新，但初始查询不同对象可能展示不同状态。
4. **Shipment 非完整交付**：独立列表/详情尚未实现，当前页面仍主要读 Package。当前 `shipment_upsert` 对同一 providerShipmentId+providerPackageId 直接返回旧记录，因此后续不同事件的状态更新也可能被当作重复忽略；Shipment单独回传也未完整处理库存/兼容Package。不能因319/318单测通过而宣称真实APP多包裹完整闭环。
5. **MCF配置是必经前置**：无绑定时会正确禁用方案查询。不是数据坏了，但演示清单必须先说明建仓绑定步骤。
6. **预览时间限制已解除**：本地估算不再10分钟过期，已有待提交出库无需撤回重建；仍校验资料、库存和绑定。

### Vendor/DF 操作必填提示

- Collect/Prepaid ASN 都应填承运商、运输参考号、日期、运输类型、按SKU精确分配的箱/托资料。
- NA场景需要SCAC；SmallParcel每箱需要跟踪号；LTL/FTL需要BOL；箱号不能重复。
- 已接受/拒绝数量不能随意降低；延期再确认使用累计数量，不是每次新增数量。
- Retail收货时，良品+短收+损坏等于本批次数量；不能只点击发货就宣称Amazon已收货。
- DF库存发布是独立能力，默认未开启publishInventory时会被拦截；不阻断接单发货，需去APP配置开启。

### Vendor/DF 阻断与不完整项

1. **Collect ASN空承运商死路**：`src/lib/vendor-workflow.ts` 仅对Prepaid强制carrier；成功ASN后UI锁定字段，发货又要求非空且与ASN一致。必须修复校验，并为已提交坏资料提供受控更正入口。
2. **错误操作入口**：普通出库详情给Vendor显示确认出库/撤回，但命令要求回Vendor来源页；按钮提交会失败，应隐藏并给来源链接。
3. **Routing失败缺重试UI**：领域有vendor_route，页面无对应按钮；本地正常job总成功，不能覆盖失败恢复演示。
4. **财务仅记录**：Invoice/ERS可登记，不等于已提交Amazon发票或实际结算；页面没有严格按paymentMethod限制类型。
5. **样本可能被跳过**：首次库存不足时collect/df-label不生成，但仍写场景导入标记，后续补库存不会自动补出该场景。

## 三、FBA 补货：逐条场景

入口：`/dashboard/fba/plans`。两行商品为耳机6、背包4，来源LAX，Seller NA / US。

| 编号 / 场景 | 初始状态 | 用户操作 | 本次结论 |
|---|---|---|---|
| FBA-20261104-107 / fba-draft | 多SKU草稿，无预占 | 保存装箱 → 生成分仓方案 → 选单/双目的地 → 运输SPD/LTL/FTL → 确认费用并生成执行 → 来源出库 → 接收 | 代码/内存路径通过，未本轮浏览器全程实测 |
| FBA-20261104-108 / fba-packed | 已装箱，有方案未选择 | 选方案/运输/费用确认 → 生成执行 → 来源出库 → 接收 | 代码/内存路径通过；修改装箱会清空方案 |
| FBA-20261104-109 / fba-split | 双仓SPD已确认，两个来源出库已打包 | 分别打开两张来源出库，填承运商跟踪号发货 → 分别登记接收 | 代码/内存路径通过；不能在已确认计划上改成LTL |

### FBA 公共后续步骤

- SPD：无需预约，打包后在来源出库发货。
- LTL/FTL：每个子货件先保存UTC送达窗口，再填写预约编号、窗口内时间、承运商凭证确认预约；两张货件分别预约后才能发运。
- 每货件登记正常/损坏收货增量与凭证，数量不能超实际发运量；所有子货件完成或短收关闭后计划关闭。
- 收货不直接增加FBA可售。库存页录入平台库存观测，填写绝对总量、预留、不可售、观测时间和报告凭证，不是把本次收到的量直接加上。
- 库存观测前必须在APP配置开启并保存读取FBA库存。

### FBA 阻断与不完整项

1. 默认配置无readInventory持久开关，最后库存观测会被拒绝，可经APP页面修复。
2. 旧样本FBA-86243001/002/003仍在旧workspace定义，但当前正式路由不加载，不可作为演示单。
3. 来源出库的“撤回出库”不适用于FBA补货，须回计划取消；任一货件已发运后不能整计划取消。
4. LTL发货按钮未提前禁用，只在提交时报告缺预约；应改善引导。
5. 短收关闭后不可重开补收；索赔仅登记数量/原因，没有赔付结果和最终财务核销。
6. 取消可释放库存，但不重开原计划；继续需新建计划。预约列表未过滤所有取消/关闭状态，可能仍显示原预约。
7. 目前接收依赖Package；只回传正式Shipment而不创建兼容Package时，会卡接收数量校验，外部Shipment整合仍需整改。

## 四、整改优先级

### P0：直接影响演示

1. 补地址修复入口，允许地址待补SO修复后继续履约。
2. 修复partial场景pending回传无job；失败回传样本同步Shipment/Package状态。
3. 修复Collect ASN必填承运商与存量坏数据更正。
4. 普通出库详情隐藏Vendor/FBA不可执行操作，并导航到来源单据。
5. Shipment状态upsert、部分发运库存和Package兼容必须统一，补正式Shipment页面。

### P1：完整场景恢复

1. Routing失败重试入口。
2. 缺货场景补货/库存调整/业务取消的恢复路线。
3. 默认库存读取配置与界面校验保持一致。
4. 场景跳过需显示原因和安全补导能力，不覆盖已操作数据。
5. 已关闭差异、取消预约和财务凭据边界明确展示。

## 五、推荐当前演示顺序

1. 仓库中心创建本地/虚拟/已绑定平台仓。
2. SO-20261104-0001：自有仓部分发货，剩余MCF，打开关联出库显式提交APP。
3. SO-AMZ-20261104-002：打包任务撤回后转MCF。
4. SO-AMZ-20261104-004：修复映射再发货。
5. SO-AMZ-20261104-006：失败回传重试，明确不重新创建配送。
6. PO-20261104-103：完整填写ASN所有运输字段后发货与收货。
7. DF-20261104-106：面单资料预览、发货、回传、收货凭据。
8. FBA-20261104-109：双出库发运、分货件接收；开启读取库存后录入观测。

不要把地址待补、缺货剩余、Routing失败、索赔赔付或真实标签作为“当前一定能从异常完整恢复”的场景演示。
