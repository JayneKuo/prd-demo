# Amazon 本地业务闭环整改状态

## 目标与边界
正式 OMS UI + 本地提供方数据，使用同一 IndexedDB 事务快照。本文是实施状态，不是全部业务完成声明。不涉及真实 Amazon、WMS、承运商、支付或银行执行。

## 已接入同一业务权威
- 销售新建、列表、详情使用 features/oms 仓储及投影，旧 MCF/独立业务工作区不再挂载在 app 路由。
- 逐行精确分配、库存预占、真实关联出库、撤回释放、发货消耗、包裹、回传及签收。
- Vendor Retail / DF 使用内部来源需求，复用仓库执行，不混入客户销售列表；DF 标签/装箱单目前仅可查看带水印资料，非真实运输面单。
- FBA 多商品装箱、单双目的地分仓、独立子货件、来源库存及出库、收货/破损/短收、明确库存观测；收货不直接推可售。SPD 与 LTL/FTL 窗口/承运商预约，出库前取消释放。
- 退货行数量、质检良品/损坏/未知分区、回原库存、实付范围退款、费用及来源结算、凭证部分/全部核销，Vendor invoice/ERS 互斥记录。
- 全局提供方运行时、原子写入、revision/幂等命令、数量和作用域校验、原始数据迁移归档。浏览器关闭时不运行，重开按持久截止时间恢复。

## 已实际浏览器验证
1. 客户订单按一行拆量：2 件仓库预占→打开同一出库→打包发货→剩余 2 件 MCF→刷新分配量仍守恒。
2. FBA：10 件装箱→双目的地方案→两张独立出库→来源出库发货。
3. Vendor DF：多行确认→固定节点仓库作业→资料预览→包裹发运→回传/签收→合格金额凭据。
4. 售后/资金：2 件包裹→退 1→良品质检回库→退款→仅选择原订单+退款形成结算→银行凭证两次核销→刷新结果保留。
5. 命令及提供方单测验证：事务失败回滚、重复命令、超量分配、预占释放/消耗、精确箱量、短收关闭、只读/范围限制、FBA 取消、卡派单货件预约约束等。

## 2026-11-05：FBM 自有仓 / 转 MCF 本轮验收
- 订单详情顶部提供独立“转 Amazon 配送（MCF）”入口和大弹窗，含原订单摘要、收件地址、FBA 逻辑仓选择、配送服务、商品库存/数量表、方案预览及固定底部确认。自有仓仍使用原执行窗口，仅选择 warehouse 库存。
- 仓库中心改为统一主数据列表与“新增仓库”，支持本地仓、虚拟仓、第三方平台仓；本地/虚拟不依赖 APP。平台仓选择已连接的 APP 仓库供应商及实际提供的外部仓资源，Amazon MCF 是其中一种能力。连接型 webhook APP 无仓库资源时只展示提示，不伪造绑定。原 MCF 绑定保持原 ID 合并进统一列表，同一 OMS 快照保存，不靠仓库名称或手填店铺 ID 路由。订单仅展示已保存绑定，不自动生成逻辑仓。库存仅来自同作用域、同账号、同站点的 FBA 记录；未同步库存不编造库存。使用原订单 Seller SKU，不选择 Amazon FC，不把原订单改成 AFN。
- 绑定仓 MCF 流程：SO → 履约与 OMS 出库单（待提交 APP，预占但无配送任务）→ 出库详情显式提交 APP → 本地适配器执行 → 回写同一出库/包裹/订单。界面明确“本地验证”，未配置真实 Amazon 后端不冒充外部推送。历史无绑定样本保留兼容执行，未自动改写历史请求。
- MCF 按本次数量查询只读本地估算（标准/加急、费用币种、送达区间、有效期）；确认时重新校验方案、连接和库存，保存方案与请求快照，回执沿用稳定请求标识。不是 Amazon 实时报价或真实 API 执行。
- 自有仓任务“撤回并转 MCF”先仅撤回，确认 cancelled 后按最新剩余预填，必须再次查询和确认才创建 MCF。撤回等待期间不重复分配，已发货/未知状态不可转换。页面转换引导为临时状态；刷新后可从已持久化原任务状态及剩余数量继续手动选择 MCF，不会自动创建配送。
- 独立浏览器实际验证：同一 FBM 行自有仓 2 件发货 + 剩余 2 件加急 MCF；既有打包任务撤回确认 + 4 件 MCF；刷新后原取消任务、MCF 请求引用和包裹保留，零页面异常。
- 独立弹窗改造后重跑浏览器脚本，两条路径及刷新均通过、零页面异常；全量 Vitest 46 文件 / 316 测试通过（含通用仓库分类、供应商仓资源、历史绑定兼容与出库提交）；浏览器验证本地仓/虚拟仓无需 APP 创建、平台仓绑定持久化及原履约链路；TypeScript 无错误。新增领域测试验证库存隔离、撤回释放、JSON 刷新、幂等、方案缺失/失效/过期拒绝、MCF 禁止手动发货。
- Shipment 已升级为 OMS 一等对象：自有仓/MCF 发运自动创建 Shipment，包含 provider、外部 Shipment/Package ID、承运商、跟踪号、发运数量、状态、回传状态和事件引用；APP 可通过 `shipment_upsert` 幂等回传，支持部分/多包裹累计、重复事件、超量拒绝、发运到签收同步，旧 packages 保留兼容。新增 Shipment 测试后全量为 47 文件 / 319 测试通过。
- 固化浏览器脚本：scripts/verify-fbm-fulfillment.cjs。先启动本地 dev 服务，再运行 `node scripts/verify-fbm-fulfillment.cjs`（需 Playwright / Chromium，可用 PLAYWRIGHT_MODULE、CHROMIUM_PATH 指定既有安装，APP_URL 指定本地地址）。脚本使用全新隔离上下文，不修改当前用户浏览器数据。

## 尚未满足完整交付标准
- 历史活跃履约缺少逐行数量：保留原始展示，禁止猜测重放，需要人工核对/修复工具，当前未提供完整修复入口。
- 未全面核验原订单所有通用动作；非实物类型暂受限，不能宣称非 Amazon 无回归。
- Vendor 复杂混装/嵌套托盘结构、接受后取消及仓库撤回、Routing/ASN 拒绝/未知场景在新统一底座的完整恢复尚需补齐。
- Seller MCF 已接通 FBM 本地方案预览与确认、请求快照及自有仓撤回转换；真实费用/预览 API、部分取消与未知回执核实、复杂分包仍未完成，不能计为全部生产场景完成。
- FBA 移除/处置/差异索赔已有有界命令，案件赔付/最终财务关闭未全部完成；库存快照细分/周期同步不等于生产接口覆盖。
- 售后当前主要为包裹退货→质检→退款，原生 AFN 平台售后、换货、仅退款、退款失败/未知及退运标签不完整。
- Vendor invoice/ERS 记录进入应收来源，但正式提交流程、拒绝/贷项/扣费争议/证据审批/回款分配尚不完整；尚不能称全财务闭环。
- 连接/策略和共用映射仍有兼容 localStorage 配置源，需继续收敛并验证迁移一致性。
- 独立页面端到端套件目前驱动脚本在临时目录，需要固化进项目并建立覆盖矩阵。

## 验收原则
已验证项仅覆盖具体列出的路径。所有业务的 happy path、partial、failure recovery、数量/库存/金额不变量及跨模块刷新结果均通过后，才能验收“全部闭环”。任何尚未实现的外部动作须明确为协同任务，不能以成功文案替代。
